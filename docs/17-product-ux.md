# Product UX & Recovery-First Interface

> **Implementation status: Partially implemented.** Sections 1-5 describe the shipped client, with the parts
> that are not built marked inline. Sections 6-7 (Component Hub, Receipts inspector) are design intent with no
> implementation at all.


## 1. User Experience Core Tenet

Fortiq helps operators answer four fundamental questions without requiring deep backup jargon:
1. **What is protected?**
2. **Where are the independent copies stored?**
3. **Who can unlock the repository, and through what mechanism?**
4. **When was actual recovery last proven and verified?**

The user experience is optimized for **verifiable recovery confidence**, not merely configuring scheduled tasks.

Detailed specifications for the visual design system, themes, and UI controls are defined in [Spec 22: Desktop UI Architecture & Visual Design System](22-desktop-ui-and-visual-system.md) and [ADR-015](adr/ADR-015-desktop-ui-architecture-and-design-system.md).

## 2. Desktop Application Architecture (`Fortiq.Desktop`)

Implemented via Avalonia UI and MVVM presentation patterns (`src/Fortiq.Desktop.ViewModels`). The desktop client features a multi-view navigation shell built on a light Fluent v2 design system ([ADR-015 Revision 1](adr/ADR-015-desktop-ui-architecture-and-design-system.md)).

The shell as implemented:

```text
Fortiq Desktop Application Shell
├── Navigation Rail
│   ├── Home      (Status summary; zero-state onboarding on a fresh machine)
│   ├── Protect   (Opens the Protection Setup Wizard)
│   ├── Backups   (Protected sources and backup/check/restore history)
│   ├── Recovery  (Per-source recovery evidence and the live proof action)
│   └── Settings  (Placeholder view; no settings are editable yet)
└── Active Workspace View
    ├── Header: Status Summary & Primary Action
    └── Content View: Cards with live health badges
```

The **Component Hub** (§6) and **Audit Receipts** (§7) views below are design intent; they have no implementation and no navigation entry.

### 2.1 Zero-State & First-Run Experience (Eliminating Startup Errors)
On a newly deployed machine where the background service has not yet produced `health.json`, the UI displays a clean, calming **Zero-State Onboarding Dashboard** rather than an intimidating error banner:
- Welcomes the operator and summarizes system readiness (TPM 2.0 status, pinned engine validity, Windows service state).
- Offers a high-visibility primary call-to-action button: **"Protect your first folder"**.
- Guides the operator smoothly into the Protection Setup Wizard.

## 3. The Protection Setup Wizard (`ProtectRepositoryWindow`)

The wizard is four setup steps followed by the key ceremony. It enforces one invariant above all: it does not finish until the operator has shown they can reproduce the recovery phrase.

### Step 1: Repository & Recovery Kit Locations
- **Native Folder Picker**: both paths are chosen through the Windows folder dialog (`StorageProvider.OpenFolderPickerAsync`), with the text box remaining editable for paths a picker cannot reach, such as `s3:` endpoints.
- **Guidance, not enforcement**: the step advises keeping the kit off the machine being backed up. *Anti-co-location heuristics that would detect and warn about a shared volume are design intent, not implemented.*

### Step 2: Source Selection
- **Native Folder Picker** for the folder to protect.
- *Directory validation (file count, total size, volume status) and exclusion presets for transient directories are design intent, not implemented.* The source is backed up whole.

### Step 3: Schedule
- **Fixed nightly recurrence at 02:00 local time**, presented as the recommended default and written as a `dailyAt` schedule file. The step says plainly that customization will come from Settings.
- *A configurable execution window is design intent.* Settings exists as a navigation entry with no editable settings behind it.
- The TPM device key is generated by `RepositoryProvisioner` during Step 4, not here, and only when the machine has a platform crypto provider.

### Step 4: Review & Create
- Summarizes the three chosen paths and the schedule before anything is created, and warns that the recovery phrase will be shown once.
- **Create** runs `RepositoryProvisioner`: it initializes the repository, writes `kit.json`, and proves the kit reopens the repository before reporting success. A failure at any point before that proof rolls the repository back.
- The schedule file is written as part of the same action. If the repository is created but the schedule cannot be written, the wizard says so on the following screens rather than reporting plain success — a repository that backs nothing up looks protected and is not.

### Step 5: Recovery Phrase (shown once)
- **4x6 Card Matrix**: the 24-word BIP-39 phrase in a numbered grid (`01. word`, `02. word`...), readable only on this step.
- **No copy affordance**: the words are rendered as plain text blocks with no copy button and no selection, so the phrase does not reach the clipboard through the UI. *This is the absence of an affordance, not an enforced block: `Ctrl+C` is not intercepted, and nothing prevents a screenshot.*
- *A printable card template is design intent, not implemented.*

### Step 6: Challenge Verification
- The wizard asks for three randomly chosen words by position (`#4`, `#11`, `#19`) and will not finish until they are typed back correctly, in order. **Entered into a single field, not discrete per-word slots** — slots are design intent.
- **Show phrase again** returns to Step 5 for an operator who did not manage to write it down. Refusing that would produce exactly the unrecoverable repository the challenge exists to prevent.
- On success the phrase is cleared from memory. Fortiq holds no other copy and cannot produce it again.

### Completion
- The final screen distinguishes "Protection is ready" from "Repository created" depending on whether the schedule was written, and states that recovery remains **unproven** until a real restore has run.

## 4. Live In-App Recovery Proof (`ProveRecoveryAdapter`)

Operators do not have to wait for an emergency to test their backups:
- The desktop interface features a prominent **"Prove Recovery Drill"** action on each repository card.
- Exercises `ProvenRestore`: restores the newest snapshot's source subtree into an isolated temporary staging directory, reconciles what landed there against what the engine reports having written, and then removes the staging directory (clearing read-only attributes, which restored files retain).
- The reconciliation is deliberately asymmetric. Bytes are compared exactly. The engine's file count is **not** compared for equality, because it counts recreated directories alongside files; the files on disk may only be fewer. An equality check there fails on every snapshot containing a subfolder.
- Content integrity is verified by the engine, which checks blob hashes during restore and fails the operation on mismatch. Fortiq does not independently re-hash restored files against source hashes; see [Spec 05, Level 2b](05-recovery-assurance.md).
- Republishes `health.json` after every attempt, so the screen reflects the state that now exists rather than the one from before the drill.
- A successful drill clears the `restore-never-proven` finding. It does **not** on its own produce a `Recoverable` verdict: an integrity check that has never run, or storage that promises nothing about retaining what is written to it, remain separate outstanding claims. The badge moves to `Recoverable` only when every claim is satisfied.

## 5. Embedded Installation & System Setup Experience (`InstallWindow`)

> *Implemented.* `InstallWindow` and `InstallViewModel` present this wizard when the desktop is launched
> outside an installed directory.

When launched outside the installed directory without a registered service, `Fortiq.Desktop` presents the **Installation & Prerequisite Wizard** ([Spec 21](21-embedded-installer-and-updater.md), [ADR-014](adr/ADR-014-embedded-gui-installer-and-updater.md)):
1. **Prerequisite Discovery Card**: Live evaluation of .NET 10 runtime, Windows hardware TPM 2.0 availability, VSS snapshot rights, and pinned restic engine binary integrity.
2. **Setup Scope & Target**: Destination directory (`%ProgramFiles%\Fortiq`), background service creation, and PATH environment configuration.
3. **One-Click Elevated Installation**: Prompts for UAC elevation, sets restrictive DACLs, creates `NT SERVICE\Fortiq`, and immediately transitions the operator into the Protection Setup Wizard.
4. **Portable Alternative**: Operators can skip installation entirely with a single click to run Fortiq as a zero-touch portable tool.

## 6. Component Status & In-App Updates Dashboard (`ComponentHubView`)

> *Design intent, not implemented.* No such view exists and there is no navigation entry for it.

Integrated directly into the desktop UI navigation rail:
- Visual inventory of all platform components: Desktop UI, Background Service, Pinned Restic Engine, and Password Broker.
- Displays version comparisons, SHA-256 binary validation badges, and Authenticode digital signatures.
- **Service Control**: View live service PID, start, stop, or restart the background engine.
- **One-Click Update**: Executes atomic transactional updates with automated rollback protection under The Update Framework (TUF).

---

## 7. Audit Receipts & History Inspector (`ReceiptsView`)

> *Design intent, not implemented.* Receipts are written to disk and read by `HealthPublisher`, but no view renders them. The Backups screen shows backup, check and restore events from the health report, which is a narrower thing.

- Chronological timeline of all backup runs, retention pruning operations, and recovery drills.
- Displays verifiable operation receipts (`receipts/*.json`) with snapshot IDs, duration metrics, byte counts, and SHA-256 receipt signatures.
- Provides proof of compliance for audits without requiring access to decrypted file contents.
